Kubernetes CSI & DNS Incident-Response Lab
Provision, break, diagnose, and document two incidents — minikube then Azure AKS
D. Grunwald · completed run

1Overview

This lab stands up a small Kubernetes cluster, injects a deliberate CSI-storage failure and a DNS-egress failure, and walks the diagnosis of each using kubectl, in-pod Linux inspection, DNS tooling, and packet capture. It runs free on minikube for rehearsal, then once on a trial-friendly Azure AKS cluster to capture evidence backed by real cloud storage.

Sequence: Rehearse on minikube until routine, then run once on AKS and keep that bundle as your portfolio artifact — cloud storage evidence reads far stronger than local hostpath.

2Performance setup (once)

minikube runs on Docker Desktop's WSL2 VM. The default 2 CPU / 3 GB allocation is too small for a Calico cluster and starves the Docker daemon — the symptom is a docker command hanging 15 seconds and start taking 30+ minutes.

Seen in practice: a two-node Calico cluster wedged Docker Desktop — docker container inspect took 18s and returned context-deadline-exceeded. Fix by reducing load (one node) and raising WSL2 memory.

Fix WSL2 resources

Create %UserProfile%\.wslconfig — save as .wslconfig, not .wslconfig.txt:

[wsl2]
memory=8GB
processors=4
swap=2GB

Apply with wsl --shutdown, restart Docker Desktop, then verify:

verify limits took
docker info --format "{{.NCPU}} CPUs, {{.MemTotal}} bytes"
One node is enough: use --nodes 1. Both faults and the full diagnosis loop behave identically on a single node; a second only adds load.

3Provision &amp; baseline (minikube)

Calico is mandatory — without a policy-enforcing CNI the DNS fault silently does nothing.

python minikube_provision_lab.py --profile irlab --nodes 1 --cni calico

Prove the storage path end to end before breaking it. On Windows the redirect needs double quotes, or cmd.exe intercepts the > before it reaches the pod:

kubectl -n irlab exec web-0 -- sh -c "echo lab-ok > /usr/share/nginx/html/index.html"
kubectl -n irlab exec web-0 -- cat /usr/share/nginx/html/index.html

You want web-0 Running and PVC data-web-0 Bound. Bound means the CSI provisioner matched your claim to a real volume.

Windows quoting: any command with > , | , or single quotes behaves differently from cmd.exe. Use double quotes, or run inside the pod with kubectl exec -it web-0 -- sh.

4Fault A — CSI storage failure

python minikube_inject_fault.py storage

A PVC bound to a non-existent StorageClass, plus a consumer pod. Diagnose:

kubectl -n irlab get pvc                    # broken-data = Pending
kubectl -n irlab describe pvc broken-data   # Events = the cause
kubectl -n irlab describe pod broken-consumer

The describe Events carry the truth:

ProvisioningFailed  persistentvolume-controller
storageclass.storage.k8s.io "nonexistent-csi-class" not found

Causal chain: missing StorageClass → PVC can't provision (Pending) → dependent pod can't get its volume → scheduler refuses to place it (FailedScheduling) → pod Pending.

Transferable habit: get shows the symptom; describe … Events shows the cause. Always read Events for the reason. Identical on AKS — only the message changes.

Capture while broken, then revert:

python minikube_collect_evidence.py --out ./evidence
python minikube_inject_fault.py --revert storage

Where AKS differs — the important one

The interview line: “I read the csi-azuredisk-controller logs and found the AttachVolume API error.” That log is the real root cause and has no minikube equivalent.

5Fault B — DNS egress block

A NetworkPolicy allowing egress on 80/443 but omitting port 53. The pod keeps Running while name resolution breaks. Transfers 1:1 to AKS.

python minikube_inject_fault.py network
The nginx pod has no nslookup: kubectl exec web-0 -- nslookup returns “executable not found” (exit 127) — a missing tool, not the DNS block. Read the exit code: 127 is not-found, not a timeout.

Reproduce correctly with the built-in verifier (runs the lookup from busybox:1.28):

python minikube_inject_fault.py network --verify

It runs two lookups: [1] from an app=web pod (policy applies → times out) and [2] from an unlabeled pod (policy does not apply → resolves). [1] failing while [2] succeeds proves the block is policy-scoped, not a broken resolver.

Confirm the resolver is sane, then name the culprit:

kubectl -n irlab exec web-0 -- cat /etc/resolv.conf
kubectl -n irlab describe networkpolicy deny-dns-egress
Controlled comparison: the unlabeled pod resolving while app=web times out isolates the variable perfectly — same cluster, same DNS, only the policy-selected pod fails.
AKS adds suspects, not steps: the method is identical; AKS adds more possible causes for the same symptom — NSGs, Azure firewall, NodeLocal DNSCache.
